# Kokoroya

Monorepo containing `kokoroya-backend` (Go) and `kokoroya-frontend` (Next.js).

## Backend — `kokoroya-backend/`

Clean architecture with layers: **repository -> service -> controller -> router**.

### Tech Stack
- **Gin** — HTTP framework
- **Postgres** — primary database
- **Redis** — cache
- **Viper** — config management (reads from `config/config.json`)
- **Logrus** — logging
- **google/wire** — dependency injection (compile-time)
- **golang-migrate** — database migration

### Folder Structure

```
kokoroya-backend/
├── cmd/api/
│   ├── main.go                  # entrypoint
│   ├── wire.go                  # wire injector definition (build tag wireinject)
│   └── wire_gen.go              # generated by `wire` — don't edit manually
├── config/
│   ├── config.json              # config values (app, postgres, redis)
│   ├── .env / .env.example      # DB credentials for Makefile migration
│   ├── type.go                  # Config struct (schema)
│   ├── config.go                # loader (viper)
│   └── wire.go                  # config.ProviderSet
├── internal/
│   ├── app/                     # App struct (bundles Config, Logger, DB, Redis) + wire.go
│   ├── modules/<domain>/        # domain-first: repository.go, service.go, controller.go, router.go (e.g. `user/`, `branch/`)
│   ├── router/router.go         # registers all module routers
│   ├── database/                # postgres.go, redis.go connections + wire.go
│   ├── middleware/               # RequireAuth, RequireRole, RequirePermission, Logger, Recovery, CORS
│   ├── jwtauth/                  # generate & parse JWT (HS256)
│   ├── session/                  # session in Redis (session:<jti> -> userID, TTL = token lifetime)
│   ├── authcheck/                # combined JWT verification + Redis session check
│   ├── response/                 # consistent response envelope helper
│   └── schema/                   # all request/response DTOs, one file per domain (e.g. userSchema.go)
├── pkg/logger/                  # logger (logrus) + wire.go
├── db/migrations/                # golang-migrate migration files
└── Makefile                      # wire, migrate-*, run, build, seed targets
```

### Convention
- Every new domain (e.g. `product`, `order`) is a new folder under `internal/modules/<domain>/` following the `user/` pattern: `repository.go` (data access) -> `service.go` (business logic) -> `controller.go` (HTTP handler, gin) -> `router.go` (`RegisterRoutes`).
- **No comments in backend Go code** (except godoc that's genuinely necessary, kept minimal). Code should be clear from function/variable names, not from comments next to it.
- Domain routers are registered in `internal/router/router.go`.
- Request/response DTOs must **not** be defined inline in `controller.go` — put them in `internal/schema/<domain>Schema.go` (see `authSchema.go`, `userSchema.go`), imported as `schema.XxxRequest`.
- API responses use a consistent envelope from `internal/response`: `response.OK(c, status, data)` for success (`{"success": true, "data": ...}`), `response.Err(c, status, message)` for errors (`{"success": false, "error": ...}`), `response.NoContent(c)` for 204, `response.AbortErr(c, status, message)` used in middleware.
- All configuration (host, port, db/redis credentials, JWT, owner seed) is defined in `config/type.go`, values in `config/config.json`, loaded via Viper.
- Dependency injection uses **google/wire**: every package exposes a `ProviderSet` (see `config/wire.go`, `pkg/logger/wire.go`, `internal/database/wire.go`, `internal/app/wire.go`), registered in `cmd/api/wire.go`. After adding/changing a provider, run `make wire` to regenerate `wire_gen.go`. `internal/router/router.go` is not part of the wire graph (built manually in `main.go` from `App`), so adding a middleware/JWT/session dependency doesn't need `make wire`.

### Auth & Permission

JWT-based login (HS256, `internal/jwtauth`) + a Redis session (`internal/session`) — the token alone isn't enough, every request is also validated against `session:<jti>` in Redis (`internal/authcheck`), so logout/revoke takes effect immediately even if the JWT hasn't expired.

- **No public register endpoint.** The only way to get a `role='owner'` account is via `make seed` (`cmd/seed/main.go`, idempotent — uses `ON CONFLICT (email) DO NOTHING`, credentials from `config.owner.email`/`config.owner.password`).
- **Only the owner can create new users** — `POST /api/users` and other user-management endpoints are gated by `middleware.RequireRole("owner")`.
- **Permissions are per-user, not per-role.** The `users.permissions text[]` column (migration `000002`) holds a list of "page keys" (e.g. `labour`, `orders`, ...) — one key per page that user is allowed to access. The owner sets/changes it via `PATCH /api/users/:id/permissions`.
- **Each page route is gated** with `middleware.RequirePermission("<page>", lookup)`: role `owner` always passes; other users are checked via `slices.Contains(permissions, page)` — permissions are fetched fresh from the DB on every request (not from the JWT claims), so a permission change by the owner takes effect immediately without requiring re-login.
- There's no separate permission/role catalog table — deliberately simplified since the page count is still small (7 pages). Add one if the number of page keys grows too large to grep manually.

7 official page keys (not 6 as originally assumed): `dashboard`, `labour`, `food-cost`, `time-station`, `employee`, `clock-in`, `schedule`. The list lives in `middleware.Pages` (`internal/middleware/middleware.go`), exposed via `GET /v1/permissions` (`internal/modules/user/controller.go` → `Permissions`, registered in `internal/modules/user/router.go`) — used by the frontend to render checkboxes on the create/edit-user permissions form. Just a constant list, not a DB table (per the original decision — small page count).

### Branches

- When the owner creates a user (`POST /api/users`), inputs are: `name`, `email`, `password`, `role`, `phone`, `tfn` (Tax File Number), `permissions` (page keys), and `branch_ids` (which branches that user can access). Password self-change is planned but not implemented yet.
- A user can have access to **more than one branch** (many-to-many via the `user_branches` table, migration `000003`), assigned by the owner — not self-service.
- After login, the frontend calls `GET /api/me/branches` (`owner` → all branches; other users → only assigned branches) to show branch options. The selected branch is sent in the `X-Branch-ID` header on every subsequent request to branch-scoped routes.
- **Branch authorization is enforced in the backend, not just a UI filter.** `middleware.RequireBranchAccess(lookup)` reads `X-Branch-ID`, `owner` always passes, other users are checked fresh against `user_branches` (`branch.Repository.HasAccess`) — on every request, no "active branch" state stored server-side (same pattern as `RequirePermission`).
- The owner manages branches via `POST /api/branches`, `PATCH /api/branches/:id` (rename/deactivate), and reassigns via `PATCH /api/users/:id/branches`.
- No branch-scoped data module exists yet (order, labour, etc.) — the middleware is ready to use once that module is built.
- Frontend: `X-Branch-ID` is already attached automatically to every request (`lib/api.ts`) from the httpOnly cookie `selected_branch` (`lib/auth.ts`). It's set via the `/select-branch` page (outside the `(app)` route group, similar to `sign-in`) right after login — auto-selected if the user has exactly 1 active branch, otherwise the user picks manually. `proxy.ts` redirects there if `auth_token` exists but `selected_branch` doesn't. Switching branch is done via the "Switch Branch" button in the sidebar footer (`switchBranchAction`, clears the cookie then goes back to `/select-branch`).
- `/store` (branch CRUD, create + toggle active/inactive) lives at `app/(app)/store/`, gated directly by `role === "owner"` (not through the `Pages`/`RequirePermission` system, since the backend also gates it with `RequireRole(owner)`, not a per-user permission).

### Running
```bash
# Start Redis via docker compose
docker compose -f docker-compose.yaml up -d

# Set up env for migration (once)
cp kokoroya-backend/config/.env.example kokoroya-backend/config/.env

cd kokoroya-backend

# Run migration
make migrate-up

# Seed the owner account (once, idempotent)
make seed

# Regenerate wire_gen.go after changing a provider
make wire

# Run the backend
make run
```

## Build Log — `kokoroya-backend/` (login + per-user permission, 2026-08-12)

Reference used: `/Users/gilbert/project/platform-auth` (JWT + Redis session pattern).

- **Starting state**: `internal/modules/user/*`, `internal/middleware/`, `internal/router/router.go` were all empty TODO scaffolds; `cmd/api/main.go` didn't start an HTTP server yet; no gin/JWT/bcrypt in `go.mod` yet.
- **Permission model**: briefly designed per-role, but the user only needed **per-user granularity** — a fixed set of pages, owner assigns which pages each user can open (not per role). So a single `users.permissions text[]` column holding page keys (e.g. `{"labour"}`) is enough, no catalog/join table needed — `middleware.RequirePermission(page, lookup)` checks `role=="owner"` (always passes) or `slices.Contains(permissions, page)`.
- **Login + session**: taken directly from the `platform-auth` pattern — JWT HS256 (`internal/jwtauth`, `RegisteredClaims` + `role` claim) paired with a Redis session (`internal/session`, key `session:<jti>` = userID, TTL = token lifetime). `internal/authcheck.Verify` combines both: JWT signature+exp **and** checking the session still exists in Redis — so logout/revoke is truly instant, no waiting for token expiry. Deliberately **did not** also build a secondary `user:sessions:<id>` set from the reference (for revoke-all-sessions) since no feature needs it, and in the reference itself it had already become a stale leak.
- **No public register.** The owner can only exist via `make seed` (`cmd/seed/main.go`, inserts with `ON CONFLICT (email) DO NOTHING`, credentials from `config.owner.*`). `POST /api/users` (create new user) is gated by `RequireRole("owner")`.
- **Import cycle**: `middleware.RequirePermission` originally wanted `user.Repository` directly → `internal/modules/user/router.go` also imports `middleware` (for `RequireRole`) → cycle. Fix: `RequirePermission` takes a `PermissionLookup func(ctx, userID) ([]string, error)` (a plain closure), not a repo type — the middleware no longer needs to know about the `user` package at all.
- **Repository consolidated**: originally had separate `FindByEmail` + `FindByID`, simplified into a single `FindBy(ctx, Filter{ID: ...})` / `FindBy(ctx, Filter{Email: ...})`, mirroring the `GetUserFilter` pattern in `platform-auth`.
- **Response envelope**: every handler originally returned an ad-hoc `gin.H{"error": ...}` in different shapes. Built `internal/response` (`OK`, `Err`, `NoContent`, `AbortErr`) — every response is now consistently `{"success": true, "data": ...}` / `{"success": false, "error": ...}`, also used in middleware for 401/403.
- **Schema split out**: request DTOs (`loginRequest`, `createUserRequest`, etc.) were originally inline in `controller.go`, moved to `internal/schema/<domain>Schema.go` (`authSchema.go`, `userSchema.go`) so controllers only contain handlers, not struct definitions.
- **Logger wired through every layer**: `pkg/logger` (logrus, already existed) was spread into `user.Service` (logs every error path with `email`/`user_id`/`jti` context) and into `middleware.Logger`/`Recovery` (uses `log.Writer()` so request logs & panic logs share the same format as the rest of the app's logs, instead of gin's default).

## Build Log — `kokoroya-backend/` (branch, 2026-08-12)

Reference used: `/Users/gilbert/project/purchase` (has a `Store` entity = branch, but its authorization was UI-only, not enforced in the backend).

- **Requirement**: after login, the user picks 1 branch from the branches they have access to. Different from the reference: branch authorization must be enforced in the **backend**, not just a UI dropdown that could be bypassed by knowing another branch's ID.
- **Many-to-many model**, not a single `branch_id` on `users` — the owner can assign 1 user to more than one branch. `branches` table + `user_branches` join table (migration `000003`), mirrors the shape of `Store` in the reference but without GORM (raw SQL + transaction, consistent with the existing `user/repository.go` pattern).
- **No new session state.** Initially considered storing the "active branch" in the Redis session (adding to `session.Manager`), but it isn't needed — just mirror the existing `RequirePermission` pattern: `middleware.RequireBranchAccess(lookup)` reads `X-Branch-ID` from the header on every request and checks fresh against `user_branches`, doesn't trust the JWT/session. More consistent with how permissions already work, and avoids adding state that has to stay in sync when branches get reassigned.
- **Owner always bypasses** in both `RequirePermission` and `RequireBranchAccess` — the same pattern used twice, no need for a "branches owned by owner" table/column since the owner simply isn't restricted by branch.
- **`GET /me/branches` is role-aware in the controller, not the repo** — `branch.Repository` has `List` (all) and `ListForUser` (joins `user_branches`) as two separate methods; the controller picks which to call based on the `role` in context. Deliberate so `Repository` doesn't hold authorization logic, just queries.
- **User creation gained new fields**: `phone` (column already existed), `tfn` (new column, plain text — not masked/encrypted yet, noted as tech debt), and `branch_ids` (initial assignment, inserted into `user_branches` in the same transaction as the `users` insert, for atomicity — see `user.Repository.Create`).
- **Self password change**: user mentioned wanting it later, deliberately not built now (no concrete requirement for the endpoint/flow yet).

### Convention: soft delete only

**Every `DELETE` endpoint in this codebase does a soft delete** — it sets `is_active = false` (or an equivalent flag), it never `DELETE FROM`s the row. This applies to branches (`branch.Repository.Delete`) and users (`user.Repository.Delete`). Deleted records stay in the DB and can be restored by flipping the flag back (the same `PATCH .../:id { is_active: true }` used elsewhere). Frontend "Delete" buttons/dialogs call the same soft-delete endpoint and show a "Restore" action once a record is inactive — don't build a hard-delete path unless explicitly asked.

### Convention: numeric inputs always use `react-number-format`

**Every editable amount/hours/rate input in `kokoroya-frontend` uses `NumericInput`** (`app/(app)/_components/numeric-input.tsx`, wraps `react-number-format`'s `NumericFormat` with `components/ui/input.tsx` as `customInput`, thousand separator, 2 decimal places) — never a bare `<input type="number">`. `AmountInput` (food-cost) and `HourInput` (labour) are both thin wrappers over it now. Reuse `NumericInput` directly (pass `className`/`maxLength`) for any new editable number field instead of writing another one-off wrapper or a plain input.

## Build Log — stale open-shift auto-close, 2026-08-13

- **Fixed a real bug**: if an employee forgot to clock out, their next clock-**in** punch (next day, whenever) would be misread as the clock-**out** for the old shift — closing a shift that spans the gap and dumping a bogus multi-hour/multi-day block onto `labour_hour_entries`, while leaving them not actually clocked in.
- **Fix**: `clock.Service.Punch` now checks the open shift's age (`time.Since(open.ClockInAt)`) against `maxShiftDuration = 16 * time.Hour`. If it's older than that, it's treated as stale — silently closed via `repo.Close` **without** calling `labour.Repository.AddHours` (so no bogus hours get added), and the punch proceeds as a normal fresh clock-in. No owner action needed; the employee's next punch self-heals it.
